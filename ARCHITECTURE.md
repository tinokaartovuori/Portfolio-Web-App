# Architecture

This file documents the architecture of this repository for anyone working on it.

## Project goal

Tino Kaartovuori's personal portfolio site. The ambition is a world-class, award-site-level portfolio: heavy custom motion/WebGL design built with modern web tooling.

Development was active Jan–May 2023, paused, and resumed in September 2026 with a modernization pass: the stack is current (Nuxt 4, three 0.185, Tailwind 4), scrolling was rebuilt on native scroll + Lenis, and content moved into a content layer.

**The copy and images in `content/` are the real ones** (replaced in September 2026: three projects, the about prose and the footer). `content/README.md` is written for whoever edits the site rather than the code, and is the right place to point someone who just wants to change text or swap an image.

Still open:

- **The film project's gallery is stills from the film.** `content/projects/3.philippines.md` (a two-hour travel film from the Philippines, in Finnish) has its card image, the YouTube link and five frames from the film as a small gallery (`galleryColumns: 3`); there are few photographs from the trip, and the body says so.
- **The load has no preloader, on purpose.** The page paints as a plain document — the hero and footer plates, the section text and the photographs as ordinary `<img>`s — and the WebGL layer takes over from that without a pop, on one shared reveal envelope. See section 12; this is now built, not open.
- **The glass/refraction work is not started.** The scene still has no lights, no environment map and no tone mapping — every material is unlit (a lit backdrop with point lights on standard materials was built and taken out again; see section 10). The hooks are in place (`scene` for lights and `environment`, `Scenario.enablePostProcessing()` for screen-space passes, real 3D tilt on the images so lighting will read), but it remains a prerequisite chain, not a tuning job.
- **The site went up on 6 September 2026**, on the Droplet it shares with the accounting app (Commands → Deployment): the build is done on the deploying machine and shipped, the Droplet only wraps it in an image. `.output` built on Windows runs on the Linux container: nothing in it is native, and the one Windows-specific thing in it, Nitro's symlinks with absolute paths to `server/node_modules/.nitro` for a package it traced in two versions, is followed by the deploy script's `tar -h` (left as links they dangle there, and every page that is not prerendered is a 500).
- **Nothing may widen the page.** An element reaching past the right edge widens a phone's layout viewport, and Chrome (device mode included) then shows the whole page zoomed out a few percent with the canvas measured against the wider width, every mesh a little off its box. `html { overflow-x: clip }` only stops a desktop from scrolling sideways; on a phone the overflow has to be clipped where it happens, as the about section does for its portrait's wash (`overflow-x-clip`), and since September 2026 the `ScrollContainer` wrapper clips too, as the guard for everything inside it (`clip`, not `hidden`, so it makes no scroll container). The first live report was exactly this: `WaveText`'s hero line was one `whitespace-nowrap` span, 418px on a 360px phone, and Chrome laid the page out 382px wide with a strip of page past the scroll track, the whole thing zoomed out a few percent and every mesh a little off its box; it now wraps between words (each word a nowrap span). Check `document.documentElement.scrollWidth` against `innerWidth` after adding anything that hangs past an edge, and check at 360 as well as 393, in Chromium's mobile emulation (`isMobile`), where the layout viewport behaves as a phone's: a desktop window of the same width shows nothing.
- **Touch overscroll is untested on a real iPhone.** The rubber band was verified with synthetic touch events in Chromium; iOS Safari's own bounce may or may not honour `overscroll-behavior: none` on the root, and the band's stand-down guard for that case has only been reasoned about, not observed.

## Architecture

The whole site is one idea: **a Three.js scene rendered behind the DOM, whose meshes are pinned 1:1 to the on-screen positions of real HTML elements, advanced by one shared clock.** Understanding that pipeline is most of understanding this codebase.

### 1. One clock drives everything

`composables/useFrameLoop.ts` owns the single `gsap.ticker` callback and runs registered callbacks in a fixed order every frame:

1. `scroll` — advance Lenis, publish position and velocity
2. `transform` — measure and place meshes against the position scroll just produced
3. `render` — draw

Register with `onFrame(stage, cb)` (returns an unregister) or `useFrame(stage, cb)` (unregisters on unmount). Both register in setup, so they run during SSR too; the loop never starts the ticker on the server (`import.meta.server` in `sync()`), because a ticker woken during prerendering kept the build process alive after the last page was written. **Never add your own `requestAnimationFrame` or `gsap.ticker.add` for anything that has to agree with scroll position** — that is exactly the desync this replaced.

`dt` is in seconds and clamped to 1/30. Two easing helpers exist and you should not write a third: `damp(current, target, lambda, dt)` from the same module for anything that only needs to approach a target, and `Spring` from `utils/spring.ts` (Framer-style `stiffness` / `damping` / `mass`, substepped semi-implicit Euler) for anything that should have mass and overshoot. `x += (target - x) * k` decays per _frame_ and so behaves differently at 60, 120 and 144 Hz.

Two small helpers sit on top of those and are shared by everything scroll- or cursor-driven: `ScrollFeel` (`utils/scrollFeel.ts`) turns the raw scroll velocity into a smoothed `velocity`, a tanh-saturated signed `drive` and a more slowly smoothed `energy`, so the images, the light fields, the dust and the marquee agree on what "fast" is; `cursorUvIn` (`utils/cursorUv.ts`) is the allocation-free "where is the pointer over this box, in UV" test.

**Every number that decides how the site feels lives in `motion.config.ts`** — scroll spring and speed cap, keyboard step, rubber-band stiffness, the shared scroll feel, the theme blend rate, the palette, the page trail shares, the scroll prompt's threshold, image trail, bubble depth, hover lift, lens size, the rim, film grain, the halation, the light fields, the dust, the grain over the page, wire shapes, index rows, marquee and magnetic pull. Tune there; the motion code reads it and nothing else should carry a magic constant.

### 2. Scrolling is native, driven by a spring, with a rubber band at the edges

The page scrolls natively. `components/ScrollContainer.vue` calls `createSmoothScroll` (`composables/useSmoothScroll.ts`), which runs in the frame loop's `scroll` stage. Find-in-page, scroll restoration and pinch zoom therefore work without any code.

**The integrator is ours, not Lenis'.** Wheel deltas (and keyboard: arrows, Page Up/Down, Space, Home, End; and same-page anchor clicks) move a _target_; the scroll position is a critically damped, velocity-capped `Spring` chasing that target, written to `window.scrollTo` every frame. Lenis' own lerp was measured and rejected: a first-order lerp restarts its velocity on every wheel notch (per-frame deltas went 8 → 11 → 14 → 15 px, one step per notch), which reads as a series of shoves; the spring keeps velocity continuous so notches blend into one swell. Lenis is still created (`lerp: 1`, `smoothWheel: false`) for what it does well — `limit` with its resize observers, the touch gesture stream, iOS quirks, the optional `syncTouch` mode — and its `virtualScroll` hook is where wheel deltas are taken over (`return false`) and touch deltas are watched. A scroll position the integrator did not write (a finger, the scrollbar, a restored position, find-in-page) is adopted as the new truth on the next frame, so it never fights the browser; adopted faster than `overscroll.bounceMaxVelocity` it is a jump rather than motion (a navigation lands the new page at the old position clamped to its height on one frame and at the top on the next) and leaves no velocity, or every scroll-driven effect saturated at once and the page arrived with its images bent and trailing. The limit it clamps to is the larger of Lenis' and the document's own, because Lenis learns a new height from a ResizeObserver a frame or two after a navigation, and clamping the router's hash scroll to the old page's limit hauled it back up. Under reduced motion the integrator is bypassed and everything is native.

**The rubber band.** Native scroll cannot go past its own edges, so `useSmoothScroll` translates the `ScrollContainer` wrapper instead (`transform: translate3d(0, overscroll, 0)`), driven by a second `Spring`. Three things feed it: wheel deltas past an edge (accumulated, then released at `overscroll.release` so the band eases home instead of snapping), a finger dragging past an edge (held while the finger is down, released into the spring on `touchend`), and momentum arriving at an edge (a share of the arrival velocity becomes a spring impulse — but only below `bounceMaxVelocity`, so a scroll-restoration jump lands dead; the integrator's own approach decelerates and never bounces). The meshes follow for free because they measure the translated DOM. The transform is removed entirely at rest so the document does not sit on a compositing layer. If iOS is ever observed rubber-banding natively (scroll position leaves `[0, max]`), the band stands down for the rest of the session rather than doubling the bounce. Two rules follow: everything that scrolls must live inside `ScrollContainer`, and nothing `position: fixed` may, because a transformed ancestor becomes its containing block.

`composables/useSmoothScroll.ts` also exports `scrollFrame` — a **plain, non-reactive** `{ y, velocity, max, overscroll, reduced }`. The WebGL layer reads this directly; Vue reactivity does not belong in a 120 Hz path. `velocity` is in **pixels per second** and is the velocity of the content _as seen_, i.e. it includes the rubber band, so a bounce deforms the images just like a scroll does. `y` stays within `[0, max]`.

Under `prefers-reduced-motion: reduce`, Lenis is created with `lerp: 1` and `smoothWheel: false`, i.e. plain native scrolling, and the rubber band never engages.

Touch scrolling stays native (`syncTouch: false`): it stays on the compositor, and the band gives it the bounce anyway. `motion.config.ts` has the switch if identical Lenis inertia on touch is ever wanted.

The OS scrollbar is hidden in CSS; `components/ScrollTrack.vue` draws the visible track/indicator from store state in the frame loop's `render` stage. It is also a scrollbar: the thin track sits in a wider invisible hit area, dragging the indicator writes the position straight to `window.scrollTo` (the integrator adopts an external position as the new truth, so the page follows the finger 1:1 without fighting the spring), and a press on the track away from the indicator glides there through the spring via `glideTo`, the one function `useSmoothScroll.ts` exports for moving the page from outside (a plain jump under reduced motion or before the integrator exists).

### 3. Pinia stores are the bus between DOM and WebGL

- `store/scrollState.ts` — `scrollY`, `scrollYVelocity` (**pixels per second**), `scrollYMax`. Mirrored once per frame from `scrollFrame` by `ScrollContainer`, for the _reactive_ consumers only (`ScrollTrack`, `BottomBar`). `ThreeScrollCanvas` does not read it.
- `store/threeObjectState.ts` — registry of DOM elements that want a 3D counterpart: `threeElementTracker` (element + object-type string) and `threeImageTracker` (image elements). `reset()` clears both; `remove(threeReference, element?)` drops a single entry — pass the node and it is only dropped if the registry still holds that exact one, so a component that lost its id to a duplicate cannot delete the winner's entry on its own unmount.

### 4. Registering DOM elements for WebGL

Two wrapper components register into `threeObjectState` on mount:

- `<ElementTracker threeReference="uniqueId" object="LightField" variant="hero">` — registers its **first slot child** and a string naming which Three class to instantiate. The optional `variant` is handed to that class's constructor as a second argument, for classes that come in presets (the hero and the footer are both a `LightField`; a `GlowPlate` is `accent` or `cool`). Attributes on the tracker fall through to its own `<div>`, which is what the parent lays out — put layout classes there, not on the child.
- `<ThreeImage threeReference="uniqueId" imageUrl="…" alt="…" />` — renders an `opacity-0` `<img>` (it exists only to be measured and to supply the texture URL, but stays in the accessibility tree) and registers it. An optional `variant` names a treatment in `motion.image.variants`, carried on the element as `data-variant` so the WebGL layer reads it the way it reads the box; `background` is the portrait under the about text. The `<img>` is `w-full` with its height left to the parent (auto by default, or `h-full` in a box that has a height of its own), and the parent's `aspect-*` or insets are what shape it. Only a laid-out image registers: one that CSS has hidden at the current breakpoint (`display: none`, no client rects) gets no mesh, and the check is repeated on window resize, so a page may hold two boxes for one photograph and the scene sees the one the viewport shows.

The registry is global and keyed by `threeReference`, so **`threeReference` has to be unique across both trackers combined** — `remove()` is keyed globally and looks in both maps. In development a duplicate logs a warning naming the id. Both wrappers deregister themselves on unmount, so a page does not need `threeObjectStateStore.reset()`; the calls the existing pages make are harmless.

### 5. The single WebGL host

`components/ThreeScrollCanvas.vue` is mounted once in `layouts/default.vue` inside `<ClientOnly>` and owns everything Three:

- `three-components/Scenario.ts` — scene + perspective camera + renderer. The camera math is the crux of the DOM↔WebGL mapping: with `perspective = 1000` and `fov = 2·atan(height/2/perspective)`, **one world unit equals one CSS pixel** at z=0, so meshes can be positioned directly from `getBoundingClientRect()`.
- `three-components/ImageManager.ts` → builds a `WavyImage` per registered image.
- `three-components/ElementManager.ts` → maps the `object` string to a class through the `OBJECT_TYPES` lookup table (`LightField`, `WireShape`). **Adding an element type is one entry there** — the `satisfies` on that literal turns a class that has drifted from the lifecycle into a compile error on the entry rather than a method that throws on the first frame. An unrecognised name renders nothing and warns in development. It also exports `TrackedObject3D`, the interface every element class has to satisfy, and `TrackedObjectName`, the union of valid `object` prop values.

Update flow, all via `watch`:

- `onFrame('transform')` → fills one reused `FrameContext` (`three-components/FrameContext.ts`: `dt`, `time`, `scroll` = `scrollFrame`, `pointer` = `pointerFrame`, `reduced`, `theme`, `heroHeight` from the scroll store) and calls `imageManager.updateImages(ctx)` + `elementManager.updateElementPositions(ctx)`. `theme` is 0 for light and 1 for dark, damped toward the resolved `useColorMode().value` at `motion.theme.smoothing` so it crosses over in the same ~600 ms as the CSS colour transition (snapped under reduced motion, where the CSS transition is 1 ms); a class that blends two palettes by it fades with the page instead of switching.
- `onFrame('render')` → `scenario.render()` — through an `EffectComposer` (RenderPass → the passes, on a multisampled half-float target), because `scenario.enablePostProcessing(passes, { output: false })` is called with the halation pass (section 6); `POST_PROCESSING` in the canvas component turns the composer off again, at which point drawing goes straight to the canvas, and it is off on a coarse pointer whatever the flag says: the multisampled target, the halation's second render and its blur are a full-screen cost per frame that a phone's GPU pays in dropped frames, for an effect that is slight at that size (the pixel ratio is capped at 1.5 there too, 2 elsewhere, in `Scenario`). It costs a full-screen target per frame, which is why there was no composer before the halation needed one; blur and glass would join the same array, before the halation. **There is no OutputPass, on purpose.** The canvas is transparent and premultiplied, and everything in the composer's target has been blended over a clear of (0, 0, 0, 0), so its colour is premultiplied by its alpha; OutputPass encodes that colour to sRGB as if it were straight, and every translucent thing — the dust, the wire lines, the faded portrait — comes out two to three times too bright. The halation pass is the last pass and encodes itself: un-premultiply, `colorspace_fragment`, premultiply again. Tone mapping, when it comes, goes in the same place. The renderer states `outputColorSpace = SRGBColorSpace` and `toneMapping = NoToneMapping` explicitly.
- `composables/usePointer.ts` → `pointerFrame`, the plain `{ x, y, hover, active }` cursor state the meshes read. `hover` is true only for a fine pointer that can hover, so a finger never triggers hover physics.
- `three-components/Particles.ts` → the one thing in the scene not pinned to an element, owned directly by the canvas component: the dust behind the page (section 10). It is updated after the managers in the `transform` stage, told about resizes, and disposed with the rest.
- `watch([width, height])` (from `useWindowSize`, 100ms trailing debounce) → full update + camera/renderer resize
- `watch(threeObjectState)` → tear down and rebuild all meshes (page navigation)
- `onUnmounted` → unregister both frame callbacks, drop every mesh and dispose the renderer

The canvas wrapper is `fixed inset-0 z-0`; page content sits above it at `z-10`. Nothing here relies on a third-party stylesheet for stacking any more.

### 6. Positioning convention for 3D objects

Every object class (`WavyImage`, `LightField`, `WireShape`) repeats the same pattern — copy it when adding new ones:

```ts
const { width, height, top, left } = element.getBoundingClientRect()
sizes.set(width, height)
offset.set(
  left - window.innerWidth / 2 + width / 2, // viewport-center-relative X
  -top + window.innerHeight / 2 - height / 2, // Y, flipped for WebGL
)
```

An element class **is** the mesh — it extends `Mesh` rather than wrapping one in an `Object3D`, so there is no inner node to keep in sync and `this.geometry` / `this.material` are the typed pair three already maintains. It has to expose `update()` (full re-measure, effects at rest), `updatePosition(ctx)` (per frame), `updateAspectRatio()` and `dispose()`: that is the `TrackedObject3D` interface `ElementManager` types its array with, so a missing method is a compile error. `ImageManager` is the outlier: it stores `WavyImage[]` and calls `update(ctx)`, `resize()` and `dispose()`, which is the smaller `DomPinnedMesh` contract `WavyImage` implements.

All of them are a `PlaneGeometry(1, 1)` scaled to the box in pixels, so UVs are 0–1 by construction; shapes such as the light field's rounded corners are a signed-distance mask in the fragment shader, fed the size in px through a uniform that has to be refreshed on every measure. A mesh placed **off the z=0 plane** that still has to match a DOM box has to multiply its position and size by `(PERSPECTIVE + depth) / PERSPECTIVE` to keep the footprint the box describes — `Scenario.ts` exports the constant; the dust's plane does exactly this from 200 units behind the page, far enough that a receding image can never pass behind it. A mesh with real depth (`WireShape`) is seen from an angle at the side of the viewport and looks sheared there; it calls `lookAt` on the camera before applying its own turn, so it reads the same everywhere on the page. Grain lives inside the shaders, never over the page: a per-pixel hash in the light field's lit parts (frost) and a faint one inside the photographs (film), both re-rolled at the one slow `motion.grain.rate` so every grain on the site lives at the same pace, and both from a sine-free hash, because the classic `fract(sin(dot(…)))` shows its period on some GPUs. The decorative materials are `transparent` with `depthWrite: false`, straight alpha over the clear-alpha-0 canvas; three draws the opaque images first and the transparent meshes after, and a plate deeper than the image can ever recede needs no `renderOrder`. Every fragment shader that writes a `Color` uniform ends with `#include <colorspace_fragment>`, for the same reason `WavyImage`'s does. The scene is rebuilt on every registration, so nothing in a class may depend on per-instance random state (the light orbits are phased by index) and the theme is read from `ctx.theme` each frame, never cached at construction.

**The texture covers the box.** A `WavyImage` maps its image onto the plane the way `object-fit: cover` would: the axis on which the image is larger than the box is cropped to the box's aspect (`uCover`, `uCoverOffset`), and the crop sits where the element's CSS `object-position` says, read on resize. So a box can be given any aspect in CSS — the home page's cards are all `aspect-video` (16:9), with a per-project `imagePosition` from the content for a file that is wider, or a separate `card` image when no crop of the lead image is the right picture — and the project page shows the lead image whole.

**The DOM box is a target, not a position.** The `<img>` a `WavyImage` follows is invisible, so the mesh is free to deviate from it by a few tens of pixels, and the physics live in that freedom: the mesh trails the box through a spring (`lag`), bends by a share of that trail, recedes in z while scrolling fast, drifts a few pixels at rest, on a wide viewport turns a little toward the viewport centre (`image.lean`: a yaw scaled by how far from the centre it sits, so the two columns face the reader; a `roll` is there for a hung-askew look instead), and under a fine pointer lifts toward the camera, tilts toward the cursor and shows a gaussian "liquid lens" (a vertex bulge plus a UV magnification and radial chromatic aberration). Every one of those is a `Spring` or a `damp()` fed by the `FrameContext`, so all of it settles the same way at 60 and 144 Hz, and every amount is a number in `motion.config.ts`. The speed effect is not in this shader but over the whole canvas: **halation** (`three-components/HalationPass.ts`, the one post-processing pass, owned by the canvas component), the photographs' highlights bleeding outward in the accent colour as on film, a little at rest and more past a hard scroll (`halation.rest`, `halation.scroll` over `start`..`full` of `|drive|`, damped). It is a threshold (linear luminance, soft knee) over a second, quarter-size render of the photographs alone (`HALATION_LAYER`, which `WavyImage` enables on itself; the light fields are bright too, and bleeding them made the hero a different hero), blurred with a separable gaussian, and added back tinted; the output is premultiplied so the halo carries alpha where it reaches past a mesh onto the transparent page. Strength and tint are set by the canvas each frame from the same `ScrollFeel` and theme the meshes use. (A soft drop shadow under every mesh, drawn from the same blur for depth on the light theme, was tried and taken out: a shadow under a photograph is a different site.) Each photograph also draws a **rim** (`image.rim`): a hairline just inside its edge in the text colour, `fwidth`-sized so it is one px whatever the plane's size or tilt, so the plane reads as a thing with an edge. The plane shows the whole photograph (`image.zoom` 1): an overscan only buys an in-frame parallax, and the one it had read as an unexplained crop. Two in-shader speed effects came before it and were taken out: a horizontal-slice glitch (the wrong era) and a frost, a mip-bias defocus with a little desaturation (too little to read). The `background` variant (`image.variants`) turns the photograph greyscale, fades it, dissolves it from a rounded shape (a superellipse inscribed in the plane, in its own UV) outward (the material goes transparent for it, so the dust shows through), turns it toward the viewport centre a few times further than the lean gives the other images, hangs it back toward the viewport centre by a share of its distance from it, so it moves slower than the page laid over it, and keeps only a share of the trail, bend, bubble, float and aberration (`motion`) and none of the cursor lens, the rim or the halation, since scenery that jumps out of the background is noise. Under `ctx.reduced` every class snaps to its box and does nothing else.

**`LightField`** is the frosted-glass light behind the hero (and, with the `footer` preset, the footer): an opaque rounded plate pushed a step past the page colour (`palette.plate`, blended in by the preset's `plate` share: darker than the page on the dark theme and lighter on the light one, so the lights have contrast to show against; opaque, so none of the dust shows through the hero or the footer) whose fragment shader lays 3–5 gaussian lights over it, "over" rather than additive so the same shader reads on both themes. A light's size follows the geometric mean of the plate's sides (a wide plate gets bigger lights than a tall one of the same height, so the empty space stays in proportion), is drawn bigger on the light theme with a broad shoulder under it (`lightField.halo`, a second gaussian twice as wide: a light on a pale plate shows only its core, where on black the same tail reads as glow), and each light is its own size by index and breathes on its own slow sine (`lightField.size`). The lights sit evenly on a ring that turns slowly as a whole, each wobbling around its seat, and every one moves through a spring. While the pointer is over the plate the **nearest** light follows it; when the pointer leaves, that light stays where it was dropped — its displacement from its seat becomes an offset it carries on from — and drifts back toward its seat at `lightField.settle`, slowly enough to read as its own wandering. Scroll energy stretches and brightens the field; the plate keeps the trail the old rectangle had; colour and alpha are dithered, because on onyx the banding lives in the low-alpha tails. Palette and per-preset numbers are `motion.palette` and `motion.lightField`.

**`WireShape`** is the solid in each index row: a cube, a pyramid, an octahedron or a globe (the `variant`), drawn as a `LineSegments` child — from an `EdgesGeometry` for the polyhedra and a hand-built parallels-and-meridians geometry for the globe, since an `EdgesGeometry` of a sphere would draw every triangle. The mesh itself has an empty geometry and an invisible material, because `wireframe: true` would also draw every face diagonal. It sits exactly on its box (the box carries the page trail), turns slowly at rest and faster with the scroll, in the scroll's direction, and under the pointer grows, brightens and tips toward it. It draws in the text colour (`palette.base`), so it reads as typography.

**Where an image is on screen decides how it moves.** The vertex shader gets the plane's centre and size in viewport units (`uScreenCenter`, `uScreenSize`, viewport spanning [-1, 1]) and computes each vertex's own screen position. While scrolling, the page behaves as a sphere seen face-on: vertices near the viewport centre move in z one way and those near the edges the other (`bubble.depth`), each mesh tilts and drifts in proportion to its screen offset (`bubble.tilt`, `bubble.spread`) — the sign of the three decides whether it bulges toward the viewer or, as set now, curves inward like a bowl, the centre sinking back and the images turning toward it — and the trail sags on the side of the plane nearer the centre — so a left-hand image and a right-hand one deform as mirror images, and an image changes shape as it travels up the screen. All of it is scaled by `energy`, the smoothed scroll magnitude (`energySmoothing`, slower than the velocity smoothing so the bubble swells and relaxes as one motion instead of pulsing with each wheel notch). At rest the mesh sits exactly on its box.

`WavyImage.ts` keeps its shaders as inline template strings, not separate `.glsl` files. The fragment shader ends with `#include <colorspace_fragment>`, which pairs with `texture.colorSpace = SRGBColorSpace` — one without the other double-encodes the image — and does the right thing under an `EffectComposer` too (linear target, `OutputPass` encodes).

### 7. Content

**The site is one page.** The home page holds the hero, the marquee, the work, the about section (`#about`) and the contact footer (`#contact`); only the projects have pages of their own, and each ends with the way on — the next project in home page order, the first again after the last, and the way back to `/#work`, under a rule — so a page does not end on a lone back link. The top bar's About and Contact are anchors into the home page (`/#about`, `/#contact`): on the home page the click is left alone and the smooth scroll's own anchor handling glides there; from a project page `TopBar` hands it to the router, which scrolls to the hash once the page is in. Both honour `scroll-margin-top`, so a section carries its own landing offset (`scroll-mt-*`, set so the anchor puts its first line at `--bar-safe + 2rem`, the hero's own top line) and its padding is only the gap to the section above; the two section breaks are the same size (work → about, about → contact, and a project page → the footer). `/about` redirects to the section (a route rule in `nuxt.config.ts`).

Text and images come from `content/`, typed by `content.config.ts` (Nuxt Content v3):

- `content/home.yml` → the `home` **data** collection (hero copy, the marquee words, section headings, the about eyebrow, the footer's `contact` block)
- `content/projects/*.md` → the `projects` **page** collection (frontmatter is the card, body is the project page; an optional `rating` — a store score out of five and its source, one store or a list of the stores that agree, drawn by `Rating.vue` on the card and under the summary of the project page as five stars filled to the score (the fill is a clipped copy over an outline, so 4.9 is four stars and nine tenths of one, and no ids reach the page) — an optional `website` beside it on the same line, labelled with its host, optional `links` on the line below the two — each drawn by `ProjectLink.vue`, with an optional `icon` for where it goes (`youtube`, `game`: a YouTube mark on a rounded plate, or a gamepad silhouette with its d-pad and buttons cut out, both in the accent), a `lang` for the language of what is there (`fi` draws the Finnish flag after the label, on the same rounded plate as the marks, and sets `hreflang`), `card: true` to show it on the home page card as well, beside "Read more", for the one link that is the work itself, and a `short` label that stands in below `sm`, because that row never wraps — and an optional `gallery` after the body, each gallery image a `ThreeImage` in a two-column grid, `wide` spanning both, so it gets the lead image's treatment; `galleryColumns: 3` sets the grid to three columns, two on a phone, closer set, for stills meant to be seen small, `wide` then spanning two at every size)
- `content/about.md` → the `about` **page** collection (frontmatter is the standfirst, the portrait, and the place and the offer — `jobTitle`, `location`, `areaServed`, an `availability` paragraph in English and in Finnish, `skills`, and the "What I offer" list as `offers` — body is the prose: two paragraphs, kept short on purpose. The page renders the body, then the English availability paragraph and the offers as a list; the Finnish paragraph is on no page — hidden text is what a search engine calls spam — and goes with the rest of these fields into the home page's JSON-LD and `llms.txt` (section 12), where a Finnish search for a developer in Turku or Helsinki finds it. The prose names no tools: the marquee and `skills` carry them. Rendered as the about section of the home page, the portrait as a `background` `ThreeImage` placed absolutely behind the section as a wash at every size, with the text laid over it in one column on the left — the canvas is behind the DOM whatever the boxes do. The photograph covers its box (cover fit, cropped on the face), so the box's shape decides the crop. From `md` up the box is the section's height less a margin (`top-[6%]`/`bottom-[6%]`, the image `h-full`) and a width per breakpoint (`74vw` at `md` down to `60vw` at `xl`), hung a little past the right edge (`right-[-12vw]`, `-8vw` from `lg`): a tall box on a narrow tablet keeps a tall slice with the face, and the box is kept inside the section because hanging back as it does (parallax) a taller one rose behind the last project's card. Below `md` the text has the whole width, so the box keeps the file's own aspect, is wider than the viewport (`124vw`, stepping down to `88vw` at `sm`) and hung well past the right edge (`-34vw` to `-24vw`), and is anchored to the section's **bottom** (`bottom-[2%]`) so the face sits behind the "What I offer" list, whose short lines leave the right side open, and the standfirst and the first paragraph stand on the plain page; anchored to the bottom, it also cannot leave the section however tall the text runs. The section is `overflow-x-clip`, so the overhang widens nothing (section 0). A portrait shown as a block of its own on a phone, less faded, was tried between the two: it read as a photograph, and this section wants a wash. A spec plate, a hardware-panel label box of key/value rows beside the prose, was built and taken out again with the longer text: it was one more thing on a section that wanted fewer)

Pages query with `queryCollection(...)` inside `useAsyncData`, and `<ContentRenderer>` renders markdown bodies. The queries go through `composables/useContent.ts`, because `useAsyncData` shares one payload per key but warns when two callers hand it different handler functions for the same key (`home` is made by the home page and the footer; `about` by the home page alone now, kept there for the same reason; `projects` by the home page and every project page, which takes its "next" from the list).

**The constraint that shapes all of this:** the WebGL layer does not read data, it reads laid-out DOM boxes. A content field is only visible to the scene once it has been rendered as a real element wrapped in `<ElementTracker>` or `<ThreeImage>`. Adding a field that never reaches the DOM adds nothing to the canvas.

Two consequences worth knowing before changing the content layer:

- `threeReference` must be unique across `ElementTracker` **and** `ThreeImage` combined — the registry's `remove()` is keyed globally across both maps. Generated ids should be prefixed per kind. A collision logs a dev-only warning.
- The scene rebuild is batched to one `nextTick`, so a burst of registrations costs one rebuild. Items arriving in _separate_ ticks still cost one rebuild each — await a whole collection before rendering its trackers.

Images referenced from content must be same-origin (i.e. under `public/`). They are loaded into a WebGL texture, so a cross-origin URL without CORS headers fails and the element collapses to zero size.

### 8. The fixed bars and the hero

`TopBar` and `BottomBar` are `Bar` components hung from the viewport edge at `--bar-offset`, with `--bar-height` for what a row of them holds; `--bar-safe` is the offset plus the **top** bar's own height (`--top-bar-height`) and `--bar-safe-bottom` the offset plus a row, all CSS variables in `index.css`, stepped per breakpoint. On a portrait phone (below `sm`, `orientation: portrait`) the top bar's controls stack down the right edge instead of squeezing into one row beside the name — the theme switch first (drawn larger there, 48×24), then the heart, then the links (`order`) — and `--top-bar-height` is the stack's height, so the hero's top padding, the anchors' `scroll-margin-top` and the top veil clear it. The rows are spaced by their visible marks rather than their boxes: a line of text carries leading the heart and the switch do not, so those two carry a margin below that makes up the difference, and every gap down the stack reads the same. Over the hero the stack is always open; once the bar has left the hero (`Bar` emits `pastHero`) it folds into a menu button in the stack's top-right corner — two hairlines that cross when open — and a press fans the four rows back out from it, staggered top-down, the closing stagger bottom-up, each row drawn up into the corner with a small turn. Folded shut, the stack is `inert` and `visibility: hidden` once faded. A navigation, a hash change, Escape, or scrolling on by more than 80px closes it, and returning to the hero simply unfolds it. While it is open `TopBar` passes `shade` to `Bar`, a second, deeper veil (`.bar-shade`: solid past the open stack, then the same feather) faded in over the ordinary one, so the fanned-out controls sit on the page colour and nothing reads through them. The button is rendered everywhere and shown by CSS only where the stack is, so hydration agrees. The bars' contents are inset from the sides by `--bar-offset` too, so the name sits in the hero plate's top-left corner as far from its side as from its top, the theme switch mirrors it in the top-right and the scroll prompt sits in the bottom-right, at every viewport; they are a frame around the plate, not a column of the page. The sections and the footer pad themselves by `--page-gutter` instead (`index.css`: at least 2.75rem on a phone, so the text stays well inside the plate, which is drawn 20px inside its box; `10vw` from `sm`), so on a wide screen the hero's text stands further in than the name above it, on purpose. `Bar` can carry a `.bar-veil`: a solid page-colour band under a long gradient mask (`mask-image`, so the global 600ms colour transition carries it through a theme switch), reaching from the viewport edge to `--bar-offset + --bar-height + 5rem` — a row of the bar, not `--bar-safe`, because the veil is only on past the hero and there a portrait phone's stack is folded to its button; sized from the open stack it reached 280px down a phone — so content scrolling under the name and the navigation fades out instead of colliding with them. Only the top bar uses it (`BottomBar` passes `veil: false`: the scroll prompt is gone before any content reaches it). The veil stays off while over the hero: `Bar` compares the hero's bottom edge (from `heroHeight` in the scroll store, set by the page) with the veil's bottom edge and fades it in once the hero has scrolled past, i.e. as the first content passes under the bar. On a page without a hero it is on from the start. The same trigger slides the top bar up to `--bar-offset-compact` (`compact` prop, a transform so it stays on the compositor) to give the scrolled page more room; over the hero it sits at `--bar-offset`. Both states are gated on `mounted`: the layout renders the bars before the page's setup has announced its hero, and a server-rendered "on" would survive hydration (class mismatches are check-only), so the server and the hydrating client always render "off". The home page announces its hero as `Infinity` before its first `await` and replaces that with the measured height. Per-control halos and a bottom veil were both tried and dropped.

The hero on the home page pads itself past `--bar-safe` at the top and `--bar-safe-bottom` at the bottom, so its text sits between the bars at every viewport; below `md` its text is bottom-aligned, so on a phone in portrait it sits in the lower part of the screen above the scroll prompt and the light field has the upper part. When it still cannot fit (a landscape phone, a small window: the section's border box grows past the viewport), the page sets `scrollPromptSuppressed` on the scroll store and `BottomBar` hides the prompt rather than letting it land on the text. A page that sets the flag clears it on unmount.

### 10. The decorative layer

Everything below is decoration on top of the pipeline above; each piece reads `pointerFrame` / `scrollFrame` in the `render` stage and honours reduced motion and coarse pointers on its own. DOM components read `matchMedia` for both **after mount**, so the server and the hydrating client always render the "off" state.

A **custom cursor** (a dot and a `difference`-blended ring) was tried and taken out again; it drew attention away from the work. A film-grain overlay over the whole viewport was taken out once too — that build tiled a small texture across the page and stepped it a few times a second, which read as a moving grid on a still page — and is back in a different form as the grain below; the two shader grains (section 6) stayed throughout.

- **The page trail** (`composables/useTrail.ts`) — one spring for the whole page, the images' own (`motion.image.lag`), integrated once per frame in the `transform` stage into the plain `trailFrame`; `useTrail(ref, share)` writes `share × trailFrame.y` to an element as a `y` transform in the `render` stage. Project text columns, the work heading, the about text, the index rows and the footer panel ride it, so text, rules, shapes and images lag and settle together as one body. The image columns are left alone: their meshes carry the trail themselves, and a trailed box under a trailing mesh would double it. A mesh pinned to a trailed element follows for free by measuring it (one frame behind, which a smoothed spring hides).
- **The dust** (`three-components/Particles.ts`) — the page's depth: layers of particles behind the page, far to near (`particles.layers`), each moving with the scroll by its own share of the page's speed (`parallax`), so the far ones creep and the near ones nearly keep up; the far ones are tiny and crisp, the near ones large and soft, like dust seen past a focused lens, which is what reads as depth. One instanced quad per particle, all of it computed in the vertex shader from index-derived seeds (a rebuild changes nothing; the CPU touches a dozen uniforms a frame): each particle drifts on its own slow loop and rises a little, breathes on its own sine, and on a fast scroll stretches into a **streak** along the scroll — a capsule in the fragment shader, its length the particle's speed on screen over a shutter time (`particles.streak`), its ink spread thinner the longer it is — so the near layers turn to short lines under a hard scroll and settle back to dots. The field wraps (`mod` in the shader, with a margin for the largest streak), the near layers step away from the pointer through a slow spring, and the whole field rides a trail of its own like the images. Everything is in viewport px on a plane 200 units behind the page, scaled by the perspective to keep the footprint; drawn first of the transparent meshes, so the light fields' opaque plates cover it. One colour, the text colour, at a low alpha, with a share of the particles in the two light hues (`tint`); every mix is done in sRGB, as the CSS transition does. Nothing draws above the hero's bottom edge (`heroHeight` in the `FrameContext`, soft over `particles.heroFade`; a hero still unmeasured cuts everything); a page without a hero has it from the top. Under reduced motion it still follows the scroll but nothing of its own moves. Earlier attempts at the depth, in order: an "edge glow" sprite per image and a cloud of soft quads (both read as blurred rectangles), smooth pebble-like forms under saturated point lights (too colourful, a 3D showcase), a faceted lit surface (a wall), free-drifting single filaments (too sparse, and the near ones crossed the images), bands of parallel waving lines rebuilt on the CPU every frame (never smooth enough), a flat geometric world as a stack of parallax layers in one fragment shader (a poster, not a place), and a **flyover** — a real 3D world (terrain, forest, city with cars and lit windows, water with weed and bubbles, clouds, an aurora) drawn as the Scenario's backdrop with its own camera flying through it and a depth-of-field blur over it. The flyover was the most built and the one taken out on purpose: it did not sit with the design — a place behind the page competes with the page — and the Scenario's backdrop hook went with it.
- **The grain** (`NoiseOverlay.vue`, in the layout as a sibling of `<main>`) — the noise over the whole page, the canvas and the text alike, so the site has one surface: a fixed canvas of grey noise, one grain per `noise.grain` CSS px, scaled up unfiltered, at a few percent opacity with no blend mode (an overlay blend was tried: its amplitude follows the base, strongest in the photographs' mid-tones and nearly nothing on the page colour, the wrong way round; the plain grey lifts the dark page by a few levels, as on the site this is modelled on). A tile of random grey is drawn once and shown at a new wrapped offset `noise.rate` times a second — four blits and no random numbers per roll — slower than the two shader grains, because this one sits over the text, where a lively grain reads as interference. Its opacity follows the theme (`noise.alpha`), gated on mount like the bars so the server and the hydrating client agree. Still under reduced motion.
- **Magnetic** (`composables/useMagnetic.ts`, `Magnetic.vue`) — an element pulled a little toward a nearby pointer through a near-critical spring and let go on leave. The pull is computed from the rest position (the rect minus the current translation), or the element would chase its own displacement. On the top bar controls, the hero CTA, the about teaser link and the footer email.
- **Index rows** (`ProjectIndex.vue`) — a box that a `WireShape` is pinned to, a rule that draws itself as the row enters the viewport, and the number in mono. Every other row is reversed (`flip`), so the solid alternates sides down the list and, on wide screens, sits opposite the image. Measured from the **row's** rect, never the rule's: a rect includes the element's own transform.
- **Marquee** (`Marquee.vue`) — a band of words between the hero and the work, holding the words twice so it loops; it runs on its own, the smoothed scroll velocity is added to it (down speeds it up, up slows or reverses it) and `drive` leans it over. The list is read once by assistive technology; the moving track is `aria-hidden`.
- **Footer** (`SiteFooter.vue`, in the layout **inside** `ScrollContainer`) — on every page. It contains nothing fixed, so it rides the rubber band and its `LightField` follows; its back-to-top link is a same-page anchor and glides through the scroll spring like `#work` does. The colophon under the panel is three columns from `md` — copyright left, links centred on a `1fr auto 1fr` grid, back to top right — and a centred stack below it (links, back to top, copyright); at `sm` the side columns were too narrow for the copyright.

**Type sizes.** The hero and the footer heading are the display sizes; everything else — eyebrows, section headings, the cards' titles and summaries, the about standfirst and prose, the project page's summary, links and prose, the colophon — was raised a fifth in September 2026 after reading as small beside them. The two prose bodies are scoped CSS (`1.2rem` on the home page, `1.275rem` on a project page); the rest is Tailwind steps, with arbitrary sizes (`text-[2.75rem]`, `text-[3.5rem]`) where a step was too coarse. The bars, the scroll prompt and the marquee were left alone: they are the frame, not the text.

Anything `fixed` is a sibling of `<main>` in `layouts/default.vue`, like the bars and the grain; nothing fixed may go inside `ScrollContainer` (section 2).

### 11. The likes and the visit log

The one thing on the site that is not prerendered: a heart in the top bar, between Contact and the theme switch, that anyone can press once, with the count beside it; and a log of page views behind it. Both need something that takes a request, which is why `nuxt build` now produces a Nitro server as well as the prerendered pages (`nitro.prerender` in `nuxt.config.ts` crawls from `/`), and why the site is deployed as a Node process rather than static files. Everything is under `server/`:

- `server/utils/db.ts` — one SQLite file, opened with Node's own `node:sqlite` (the binding Nuxt Content already uses, so nothing to install or compile), at `runtimeConfig.dataDir` (`NUXT_DATA_DIR`; `.data/site/` in development). Four counter tables: `counters` (the likes), `views` per day and path, `sessions` per day (the visitor count: first views of a browser session) and `referrers` per day and host. Nothing that identifies a person is written — no address, no user agent, no id.
- `server/api/likes.get.ts` / `likes.post.ts` — the count, and one more. `server/api/visit.post.ts` — one page view, with `session: true` and the referrer (reduced to its host, own host dropped) on the first view of a session; crawlers declined by user agent. `server/api/stats.get.ts` — the numbers as JSON over the last `?days=` (30), guarded by `runtimeConfig.statsKey` (`NUXT_STATS_KEY`, as `?key=` or a bearer token); with no key set it answers in development only.
- `server/utils/rateLimit.ts` — an in-memory count per client address and action, behind both writes (ten likes an hour, a hundred and twenty views a minute). It reads `X-Forwarded-For`, which Caddy sets, and forgets on restart; it is there to stop a script, not to be a store.

On the client, `composables/useLikes.ts` fetches the count **after mount** — never during prerendering, or a build would freeze a number into the page — and remembers having liked as a flag in `localStorage`, so the heart stays filled across visits and the server's guard stands behind it for anyone who clears it. A press moves the count at once and the server's answer replaces it, or takes it back on failure. `components/LikeButton.vue` is the heart, set in the same type as the links: the fill and the count are the only server-rendered state (both "unknown", so hydration agrees; the count is shown compact, at most four characters — `1.2k`, `123k`, `1M` — by `utils/formatCount.ts`, the exact number in its `title`, and its box takes the number's own width so the gap to the switch is the bar's gap), over the hero it stays in the text colour (hollow, or filled once given) and takes the accent only after the bar has left the hero (`Bar` provides `pastHero` under `BAR_PAST_HERO`, `composables/useBar.ts`), where the rose reads against the page colour rather than the lights; a press throws the heart to `like.pop` and lets `like.popSpring` bring it back with an overshoot, leaves a ring growing to `like.ring` and fading at `like.ringSmoothing`, and rolls the number up to the new one; a fine pointer lifts it by `like.hoverLift`. All of it in the frame loop's `render` stage through the shared `Spring` and `damp`, and none of it under reduced motion, where the fill and the number just change. `plugins/visit.client.ts` reports every page view: once at `app:mounted` and once per route change (the initial navigation is skipped, `app:mounted` reports it; a hash jump is not a view), with a `sessionStorage` flag marking the first view of a session. A failed request is nobody's problem: the heart stays mute and the view goes uncounted.

Broader analytics (unique visitors across sessions, countries, devices, a dashboard) are deliberately not built here: that is a product, and GoatCounter runs beside the app on the Droplet for it (`docker/goatcounter`, the `stats` service in `docker-compose.yml`, one binary and a SQLite file on the `stats` volume; the dashboard is `stats.kaartovuori.fi`). The visit plugin counts each view into it as well as into `/api/visit`: it loads `count.js` from that instance itself, after mount, with the script's own page-load count off and calls `count()` where it reports a view, so the two logs count the same thing. Its origin is `runtimeConfig.public.goatcounter`, which the prerendered pages read at build time, so it is set for `nuxt build`, not for the server; empty, only the site's own log counts. A content blocker stops GoatCounter and not the site's own log, which is why both exist and why the two numbers will differ.

### 12. Loading like a plain page, and SEO

**The load has no preloader.** The whole point is that the site paints as an ordinary document and the WebGL layer takes over from it invisibly, so nothing pops in at its own time. Two facts make it simple: the DOM is always above the canvas (`main` z-10, canvas z-0), and element-bound meshes are rebuilt on every registration burst and navigation. So every handover is _draw the WebGL version fully under the DOM version, hide the DOM version the next frame, then ramp the effects_ — never a crossfade, which would let the page colour bleed between two half-opaque layers. And each element's "arrival" clock lives on the DOM element (`components/three-components/Arrival.ts`, a `WeakMap`), not on the mesh, so a rebuild does not replay it.

- **The reveal envelopes** are in `composables/useReveal.ts`: `revealFrame.page` (from the first client frame; the scroll-track indicator and the grain fade in on it) and `revealFrame.scene` (from the frame after the first WebGL render, once the hero is measured; the dust fades in on it). `FrameContext` carries `rendered` and `reveal`. All the timings are `motion.reveal`. Everything else that used to pop is instead **correct in the server HTML**: the theme switch is pure CSS from the `dark` class (`ToggleSwitch.vue`), the scroll prompt shows by default on the home route, the index rules snap to full width on the first frame, the like count's box is the number's own width (no reserved width: the count is at most four characters, `utils/formatCount.ts`, and the gap to the switch stays the bar's gap), and a project page declares `definePageMeta({ hero: false })` so `Bar.vue` renders the scrolled (veil + compact) state from the server rather than animating into it.
- **The plates** (hero, footer) are painted by the page from the first frame: a `[data-plate]` div in the light field's box, in exactly the colour the shader starts from — `utils/plate.ts` computes `mix(page, plate, plateMix)` in linear light and encodes it (light `#f9f9fc`, dark `#050508`). When the `LightField` mesh has drawn under it in the same colour it hides the div (`visibility`, not a transition) and ramps its lights in; the mesh's dither is scaled by the same envelope so the plate is flat until the lights arrive. Without WebGL the div simply stays: it _is_ the design's frame.
- **The photographs** are real, visible `<img>`s (`ThreeImage.vue` renders a `<picture>` with AVIF/WebP/JPEG `srcset`, `width`/`height`, lazy below the fold, `priority` on a project's lead) — they load like on any page. The `WavyImage` mesh is invisible until its texture is ready, textures itself from that very `<img>` (`components/three-components/TextureCache.ts`, one fetch and one decode shared with the DOM, keyed by `currentSrc`, refcounted across rebuilds, uploaded one a frame by `ImageManager`), and then over `motion.reveal.image` fades the `<img>` out over the finished opaque mesh while the rim, trail, lean and float come in (all gated by the arrival, so the two agree to the pixel through the handover). The texture comes from an `ImageBitmap` copy, not the element, because three sizes a texture from `image.width` — the `<img>`'s CSS width, not the bitmap's. Under reduced motion every handover is one frame; on a lost context or unmount the canvas calls `restoreDom()` and the `<img>`s and plates come back.
- **three.js is off the critical path**: `<LazyThreeScrollCanvas>` in the layout, with `plugins/three-warm.client.ts` starting the chunk's `import()` at `app:created` so it downloads alongside hydration. The first drawn frame waits on `renderer.compileAsync`, so the shader compile does not stall it.

**SEO and AI-search.** Hand-rolled, no SEO module. `runtimeConfig.public.siteUrl` is the origin; `composables/useSiteUrl.ts` makes URLs absolute; `composables/useSeo.ts` sets title, description, canonical, Open Graph (absolute `og:image` from the build's 1200×630 crop) and the Twitter card, and `useJsonLd` emits a `@graph`. The home page is a `WebSite` + `Person` built from `about.md`'s frontmatter and `home.yml`: `address`, `homeLocation`, `workLocation` and `hasOccupation` in the cities of `areaServed`, `knowsLanguage`, a language-tagged `description` (the English site description and the Finnish availability paragraph), `knowsAbout` from the marquee and `skills`, `makesOffer` as one `Service` per offer with `areaServed`, and `sameAs` the socials. That and the `llms.txt` brief (occupation, location, the about prose in both languages, the offers, the skills) are what let an answer engine match "a developer in Salo, Turku or Helsinki" to this site; nothing else on the site names a place. The default title lives in the layout's title template only — a static `app.head.title` would be run through that template and come out with the name twice; a project page is the type its frontmatter's `schemaType` names (`SoftwareApplication` with rating and offer, `VideoObject` with the YouTube embed and `inLanguage`, `VideoGame` with its repo, or `CreativeWork`) plus a `BreadcrumbList`, built in `composables/useProjectJsonLd.ts`. `server/routes/{sitemap.xml,robots.txt,llms.txt}.ts` are prerendered (`nitro.prerender.routes`) and read the content server-side with `queryCollection(event, …)`. The `<footer>` is a sibling of `<main>` (a top-level `contentinfo`), the error page is `noindex`, years are `<time>`, and the favicon set and web manifest are generated with the images.

## Known rough edges

- gsap has been removed: the frame loop (`composables/useFrameLoop.ts`) runs its own `requestAnimationFrame` ticker, and the two decorative timelines (`ToggleSwitch`, `WaveText`) are now `damp`/sine in the render stage. Do not add it back for a ticker or a quickSetter — write the style directly with a change guard, as `useTrail`/`useMagnetic` do.
- `npx prettier --check .` fails on most files: the installed `prettier-plugin-tailwindcss` sorts Tailwind classes differently from the version that originally formatted the repo. Pre-existing drift; it wants a single dedicated `npm run format` commit, landed on its own so it does not bury real diffs.
- No `.gitattributes` and `core.autocrlf=true`, so the working tree is a mix of CRLF and LF. Prettier's default `endOfLine: 'lf'` flags every CRLF file even when the content is already formatted.
- Every page has an `<h1>` (the hero lead on the home page, the title on a project page, the message on the error page).
- The `webglcontextlost` fallback (the page returns to its `<img>`s and CSS plates) has been reasoned about and exercised with a forced context loss in Chromium, but not seen on a real driver crash.
